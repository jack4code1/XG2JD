# 秒杀并发与一致性实验报告

实验日期：2026-08-19  
原始数据：`benchmark-results-2026-08-19*.json`、`benchmark-sustained-2026-08-19.json`  
复现脚本：`scripts/benchmark_matrix.py`

## 1. 实验目的

验证系统在不同并发度下的吞吐和延迟，并检查以下业务不变量：

1. Redis 库存不会扣成负数。
2. 成功请求数、MySQL 订单数和库存扣减数一致。
3. 并发请求不会生成重复订单号。
4. 同一用户并发抢券只能成功一次。
5. RabbitMQ 异步订单最终能够全部落库。

| 中间件 | MySQL、Redis、RabbitMQ，均运行于本机 Docker Desktop |

该结果是本地单机实验数据，不代表生产多机部署能力。客户端和服务端位于同一主机，不包含公网网络延迟。

## 3. 实验方法

- 用户注册和登录在计时前完成，计时区间只包含 `POST /api/seckill/execute`。
- 每个吞吐实验使用独立优惠券，库存等于请求数，避免不同轮次相互污染。
- 每个请求使用不同用户和设备指纹，排除一人一单与防刷规则对吞吐矩阵的干扰。
- 每轮结束后轮询全部成功订单，确认订单已经由 RabbitMQ 消费并写入 MySQL。
- 读取商户接口中的 Redis 实时库存，并额外通过 MySQL 和 RabbitMQ 命令进行最终核对。
- 并发矩阵执行 3 个独立轮次，每档每轮 400 请求；另执行 200 并发、2,000 请求的持续实验。

复现命令：

```powershell
python scripts/benchmark_matrix.py `
  --concurrency 10,50,100,200 `
  --requests 400 `
  --output docs/benchmark-results.json
```

## 4. 三轮并发矩阵

每档累计 1,200 请求，表中吞吐与延迟为 3 轮平均值。

| 并发数 | 平均吞吐 | 吞吐范围 | 平均 P50 | 平均 P95 | 平均 P99 | 成功率 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 179.89 req/s | 140.81–224.92 | 52.63 ms | 68.14 ms | 185.89 ms | 100% |
| 50 | 387.63 req/s | 346.11–417.28 | 122.68 ms | 139.64 ms | 144.51 ms | 100% |
| 100 | 387.84 req/s | 350.73–406.67 | 242.25 ms | 265.86 ms | 271.48 ms | 100% |
| 200 | 392.73 req/s | 391.89–394.33 | 432.57 ms | 475.73 ms | 480.20 ms | 100% |

三轮矩阵共发送 4,800 个请求：

- 成功 4,800，失败 0。
- 重复订单号 0。
- MQ 超时后仍未落库的订单 0。
- 12 个吞吐测试活动的 MySQL/Redis 库存全部一致。

10 并发第一轮 P99 出现 417.47 ms 冷启动离群值，因此报告保留三轮均值及范围，不只展示最优轮次。吞吐在 50 并发后接近平台期，而延迟随并发继续增加，说明当前单实例瓶颈已由客户端并发转移到应用/MQ确认/数据访问链路。

## 5. 200 并发持续实验

| 请求数 | 成功数 | 耗时 | 吞吐 | 平均 RT | P50 | P95 | P99 | 最大 RT |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2,000 | 2,000 | 4.7683 s | 419.44 req/s | 459.05 ms | 462.84 ms | 486.92 ms | 491.31 ms | 504.07 ms |

实验结束后：Redis 库存为 0，MySQL 可见订单 2,000，唯一订单号 2,000，未发现超卖、重复订单或 MQ 落库缺失。

## 6. 库存耗尽实验

配置：100 并发、300 请求、初始库存 100；共独立执行 4 轮。

每轮结果均为：

- 成功 100，失败 200。
- 200 个失败请求全部返回“优惠券已抢光”。
- Redis 和 MySQL 最终库存均为 0，没有负库存。
- MySQL 订单数为 100，订单号全部唯一。

结论：Lua 中的库存预检与扣减位于同一原子脚本内，售罄竞争下未出现超卖。

## 7. 同一用户并发实验

配置：同一用户、50 并发、100 请求、初始库存 100；共独立执行 4 轮。

每轮结果均为：

- 成功 1，失败 99。
- 99 个失败请求全部返回“您已参与过本次活动”。
- 最终库存 99，MySQL 只生成 1 个订单。

结论：即使多个请求同时绕过进程内 Bloom Filter 预筛，Redis Lua 中的 Set 校验和用户标记仍能保证一人一单。

## 8. 全量一致性核对

包含预热、矩阵、持续、售罄和同用户竞争实验在内：

```text
Prometheus seckill_requests_total{result="success"} = 7,324
MySQL 秒杀订单数                                  = 7,324
MySQL DISTINCT order_no                           = 7,324
```

三者完全一致；检查时 `order.create.queue`、`dead.letter.queue` 的 ready/unacknowledged 均为 0。
